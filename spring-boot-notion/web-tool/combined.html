1. Another ConditionalOnMissingBean Example

Open Original Article

Another ConditionalOnMissingBean Example

Code Example

Imagine building a notification module where a default console logger is used unless a real email sender is provided.

Java

public interface NotificationService{
    void send(String message);
}

// 1. The Default Implementation
@Component
public class ConsoleNotificationService implements NotificationService{
    @Override
    public void send(String message){
        System.out.println("CONSOLE LOG: " + message);
    }
}

// 2. The Configuration with Conditional Logic
@Configuration
public class NotificationConfig{

    @Bean
    @ConditionalOnMissingBean(NotificationService.class)
    public NotificationService defaultNotificationService(){
        // This only gets created if no other NotificationService bean exists
        return new ConsoleNotificationService();
    }
}

If you start your application right now, Spring Boot injects ConsoleNotificationService. However, if you add your own custom implementation elsewhere in your project:

Java

// 3. The Custom Override created by the developer
@Component
public class SendGridNotificationService implements NotificationService{
    @Override
    public void send(String message){
        // Logic to send real emails via SendGrid API
        System.out.println("EMAIL SENT VIA SENDGRID: " + message);
    }
}

Spring detects that a NotificationService bean (SendGridNotificationService) is already present. It automatically backs off from creating the conditional default, ensuring your custom logic takes over without throwing duplicate bean definition errors.

Startup Workflow

  1. Component Scan Phase

    Spring Boot boots up and begins scanning the project's packages for classes annotated with @Component, @Service, or @Configuration.

  1. Detecting Custom Implementations

    Spring discovers the developer-created SendGridNotificationService (annotated with @Component) and prepares to register it into the application context as a NotificationService bean.

  1. Evaluating Conditional Logic

    Spring processes the NotificationConfig class and reaches the defaultNotificationService() method, which is guarded by @ConditionalOnMissingBean(NotificationService.class).

  1. Condition Check Result

    The container checks its registry, sees that SendGridNotificationService has already been registered, and determines that a NotificationService bean is not missing. The condition evaluates to false.

  1. Backing Off

    Spring Boot skips the execution of defaultNotificationService(). The fallback console logger is never instantiated, avoiding duplicate bean definitions.

  1. Runtime Injection

    Whenever a component requests a NotificationService, Spring seamlessly injects the custom SendGridNotificationService, ensuring email delivery runs by default without manual wiring changes.

2. Beans

Open Original Article

Beans

In plain English: A Spring Bean is simply a Java object that Spring manages for you.

Normally, you do MyClass obj = new MyClass(). With Spring Boot, you let Spring create and hold the object in its IoC Container (the "warehouse"). Whenever you need it, Spring hands it to you (Dependency Injection).

Here is the golden rule: Every Service, Repository, Controller, Configuration, and Component you write is a Bean.

But how do you tell Spring to manage an object? There are two distinct ways, and you must know both.

Method 1: Class-Level Annotations (The Easy 95% Way)

You put an annotation directly on your class. Spring scans the package, finds it, and creates a Bean automatically.

AnnotationWhat it means practicallyWhen to use
@Component"Spring, manage this generic class."Utility classes, helpers.
@Service"Spring, manage this as business logic."All your business logic classes.
@Repository"Spring, manage this for DB access."JPA Repositories, DAO classes. (Also catches DB exceptions).
@Controller / @RestController"Spring, manage this as a web endpoint."REST API controllers.
// 1. Tell Spring to manage this class as a Bean
@Service 
public class TaxCalculator {

    // No @Autowired needed on constructor for a single constructor
    public TaxCalculator() {
        System.out.println("TaxCalculator Bean Created!");
    }

    public double calculate(double amount) {
        return amount * 0.18;
    }
}

// 2. Some other class asks for it
@RestController
public class BillController {
    private final TaxCalculator taxCalculator;

    // Spring injects the TaxCalculator Bean here
    public BillController(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }
}

Method 2: The @Bean Method (The Explicit 5% Way)

You cannot put @Component on third-party classes (like RestTemplate, ObjectMapper, or AmazonS3Client) because you don't own the source code!

The Limitation: First-Party vs. Third-Party Code

  • First-Party Code (Your Code): You wrote it. You can open UserService.java in your IDE and put @Component or @Service directly above the class definition. Spring scans your project, finds the annotation, and creates the bean.
  • Third-Party Code (External Libraries): These are pre-compiled and read-only. You cannot open the class file for RestTemplate or ObjectMapper to add annotations to it.

For these, you manually tell Spring: "Hey, when I call this method, take the object it returns and manage it as a Bean."

You do this inside a class annotated with @Configuration.

The Solution: @Configuration and @Bean

Because you cannot tell the third-party class to register itself, you must tell Spring how to create an instance of it inside your own code using a @Configuration class and a @Bean method:

Java

@Configuration
public class AppConfig{

    // Spring runs this method and manages the returned instance as a bean
    @Bean
    public RestTemplate restTemplate(){
        return new RestTemplate();
    }

    @Bean
    public ObjectMapper objectMapper(){
        return new ObjectMapper();
    }
}

Once defined this way, Spring places these instances into the ApplicationContext, allowing you to inject them into your services just like any other @Component:

Java

@Service
@RequiredArgsConstructor
public class ApiClientService{

    private final RestTemplate restTemplate; // Injected automatically
    private final ObjectMapper objectMapper; // Injected automatically
}

The Most Important Spring Boot Twist: @ConditionalOnMissingBean

This is what makes Spring Boot magical. When you autowire a Bean, Spring Boot says: "I have a default Bean, but if you create your own, I'll use yours instead."

Spring Boot has auto-configuration classes running in the background for common infrastructure (like Jackson's ObjectMapper, a DataSource, or builders).

Almost every default bean definition in Spring Boot is marked with this annotation:

Java

@Bean
@ConditionalOnMissingBean // "Only create this if the user hasn't created one!"
public ObjectMapper objectMapper(){
    return new ObjectMapper();
}

When your application boots up:

  1. Spring checks your code first: Did you declare your own @Bean for that class?
  1. If YES: Spring registers your bean. The conditional check fails, so Spring Boot backs off and does not create its default.
  1. If NO: Spring Boot creates and registers its default bean for you.

an example where Spring Boot does provide a full default bean that completely steps aside when you write yours, look at Jackson's ObjectMapper:

Java

@Configuration
public class JacksonConfig{

    // The moment you define this, Spring Boot disables its auto-configured ObjectMapper
    @Bean
    public ObjectMapper customObjectMapper(){
        ObjectMapper mapper = new ObjectMapper();
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        return mapper;
    }
}

Without this method, Spring Boot supplies a default ObjectMapper. With this method present, Spring Boot's @ConditionalOnMissingBean detects your bean, backs off, and wires your custom version everywhere across your application.

Bean Scopes (Singleton vs Prototype)

By default, every Bean in Spring Boot is a Singleton. This means Spring creates only one instance of that class for the entire application, and every class that injects it gets the exact same object in memory.

Singleton Scope (Default)
When a bean is defined as a singleton, the Spring container creates only one shared instance of that bean for the entire application context. Every time that bean is requested or injected anywhere in your code, Spring returns the exact same object reference. This is ideal for stateless components like service layers, data access objects (DAOs), and utility beans.

Prototype Scope
When a bean is configured as a prototype, a brand-new instance is created every single time the bean is requested from the container. If you inject or request a prototype bean in multiple places, you receive a completely distinct object instance each time. This is necessary for stateful objects where data shouldn't be shared or overwritten globally.

Code Example

Java

@Component
// Singleton scope (default) - only one instance exists application-wide
public class InventoryService{
    public void checkStock(){
        // Stateless business logic
    }
}

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
// Prototype scope - a fresh instance is generated on every request
public class ShoppingCart{
    private List<String> items = new ArrayList<>();

    public void addItem(String item){
        items.add(item);
    }
}

In this setup, InventoryService is shared safely across the application since it doesn't hold user-specific data. Conversely, ShoppingCart maintains user-specific state, meaning a prototype scope ensures different threads or user sessions receive independent carts rather than conflicting over the same instance.

Bean Naming (The Silent Bug Maker)

If you don't specify a name, Spring Boot uses camelCase of the class name.

  • TaxCalculator class → Bean name is taxCalculator
  • RestTemplate class → Bean name is restTemplate

How does Spring inject dependencies? Does it check the type or the name?

Resolution Order

When Spring encounters an injection point (like @Autowired), it resolves candidates through a fixed sequence:

  1. Match by Type: Spring scans the ApplicationContext for all beans assignable to the target dependency's type (including interfaces and parent classes).
    • Exactly 1 match: It injects that bean directly.
    • 0 matches: It throws NoSuchBeanDefinitionException.
    • 2 or more matches: It moves to ambiguity resolution.
  1. Check for @Primary: If multiple beans match the type, Spring checks whether exactly one of them is annotated with @Primary. If so, that bean wins.
  1. Check for @Qualifier: If specified at the injection point (e.g., @Qualifier("creditCardService")), Spring matches against the qualifier value declared on the candidate bean.
  1. Fallback: Match by Name: If multiple candidate beans match the type and no @Primary or @Qualifier settles it, Spring compares the field or parameter name to the candidate bean names (IDs).
    • If one candidate's bean ID matches the variable name, it injects it.
    • If none or multiple match, it throws NoUniqueBeanDefinitionException.
public interface PaymentGateway {}

@Component("stripe")
public class StripeGateway implements PaymentGateway {}

@Component("paypal")
public class PayPalGateway implements PaymentGateway {}

@Service
public class CheckoutService {

    // 1. Spring looks for beans of type PaymentGateway -> finds [stripe, paypal]
    // 2. Ambiguity exists -> checks variable name: "paypal"
    // 3. Injects PayPalGateway
    @Autowired
    private PaymentGateway paypal; 
}

3. Components

Open Original Article

Components

In plain English: A Component is any Java class that you mark with a special hat (annotation) to tell Spring: "Hey, please create an instance of this class, keep it in your warehouse, and manage its entire lifecycle for me."

But here is the secret most tutorials don't tell you: You will almost NEVER use the plain @Component annotation in a real project. Instead, you use its specialized "children" because they make your code 10x more readable.

The Component Family Tree (The Hierarchy)

Spring Boot has 4 main stereotype annotations. They are all exactly the same under the hood (they all create Beans), but they serve different human purposes:

AnnotationWhat it meansWhen to use
@ComponentThe generic parent.Use for pure utility classes that don't fit anywhere else (e.g., a PasswordEncoder, a DateFormatter).
@ServiceHolds Business Logic.Use for all your service layer classes that perform calculations, validations, and orchestrate repositories.
@RepositoryTalks to the Database.Use for Data Access Objects (DAOs). Special perk: Automatically catches database-specific SQL exceptions and converts them into Spring's unified DataAccessException.
@Controller / @RestControllerHandles Web Requests.Use for REST API endpoints that map HTTP requests to Java methods.

Practical Example: The Four Components Working Together

Let's build a tiny E-commerce feature to place an order. You will see all 4 stereotypes in action simultaneously.

java

// 1. @Repository - Talks to the database
@Repository
public class OrderRepository {
    public void saveToDb(String orderId) {
        System.out.println("Saving order " + orderId + " to the database...");
        // If a SQLException happens here, Spring wraps it into DataAccessException automatically.
    }
}

// 2. @Component - A generic utility (doesn't fit Service/Repository)
@Component
public class OrderNumberGenerator {
    public String generate() {
        return "ORD-" + System.currentTimeMillis();
    }
}

// 3. @Service - The core Business Logic
@Service
public class OrderService {

    private final OrderRepository orderRepository;      // Injected
    private final OrderNumberGenerator numberGenerator; // Injected

    // Constructor Injection (The Gold Standard)
    public OrderService(OrderRepository orderRepository, OrderNumberGenerator numberGenerator) {
        this.orderRepository = orderRepository;
        this.numberGenerator = numberGenerator;
    }

    public void placeOrder() {
        String orderId = numberGenerator.generate(); // Use utility component
        orderRepository.saveToDb(orderId);           // Use DB component
        System.out.println("Order placed successfully!");
    }
}

// 4. @RestController - Handles HTTP Requests (Web Layer)
@RestController
@RequestMapping("/orders")
public class OrderController {

    private final OrderService orderService; // Injected

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping("/place")
    public String placeOrder() {
        orderService.placeOrder();
        return "Order placed!";
    }
}

Notice the flow: When a user hits POST /orders/place, Spring calls the Controller, which calls the Service, which calls the Repository and the Utility Component. All 4 classes are components, and Spring injected them automatically.

Advanced: Customizing Component Names

By default, Spring uses camelCase of the class name as the Bean ID:

  • OrderNumberGenerator → Bean name is orderNumberGenerator.
  • OrderService → Bean name is orderService.

You can change the name manually using the annotation parameter:

java

@Component("utilities") // Now you must use @Qualifier("utilities") to inject it.
public class OrderNumberGenerator { ... }

4. Configurations

Open Original Article

Configurations

To understand Spring Boot Configuration, think of it as the "control panel" of your application.

It is everything that determines HOW your app runs, without changing your Java source code. Do you need to run on port 8081 instead of 8080? Change the database URL? Turn on debug logs? That is all Configuration.

In Spring Boot, configuration is split into two completely different worlds. Mixing them up is the #1 mistake junior developers make:

  1. Externalized Configuration (Data/Values): Database URLs, API keys, server ports. Lives in application.properties / application.yml.
  1. Java Configuration (Beans/Setup): Creating and wiring up Beans (like RestTemplate, SecurityFilterChain). Lives in classes annotated with @Configuration.

Here is exactly how both work, with rock-solid examples.

Part 1: Externalized Configuration (The application.yml file)

This is where you store values that change per environment (Dev, QA, Prod). Spring Boot reads this file automatically on startup.

Example using application.yml (modern) vs application.properties (older):

Old way (properties - flat & repetitive):

properties

server.port=8081
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=secret123

New way (YAML - hierarchical & human-readable):

yaml

server:
  port: 8081

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret123

# Custom application-specific settings
app:
  name: E-Commerce API
  max-retry-attempts: 3
  email:
    host: smtp.gmail.com
    port: 587

Part 2: Reading Configuration in Your Java Code

You never hardcode "localhost" or "8081" in your classes. You read them from the YAML file using two methods:

Method A: @Value (Use for 1–2 simple values)

java

@Service
public class EmailService {

    @Value("${app.email.host}")   // Reads "smtp.gmail.com"
    private String emailHost;

    @Value("${app.email.port}")   // Reads "587"
    private int emailPort;

    @Value("${app.max-retry-attempts:5}") // Reads 3, but defaults to 5 if missing!
    private int maxRetries;

    public void send() {
        System.out.println("Connecting to " + emailHost + ":" + emailPort);
    }
}

Downside: If you have 20 related properties, your class gets cluttered with 20 @Value annotations.

Method B: @ConfigurationProperties (The PRO Way - USE THIS!)

This binds a whole group of properties into a single, type-safe Java POJO. This is the gold standard in professional Spring Boot.

Step 1: The properties file (application.yml)

yaml

aws:
  access-key: AKIAIOSFODNN7EXAMPLE
  secret-key: wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
  region: us-east-1
  s3:
    bucket: my-app-bucket
    timeout: 3000

Step 2: The Java POJO to hold them

java

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.stereotype.Component;

@Component
@ConfigurationProperties(prefix = "aws") // Tells Spring to map everything under "aws"
public class AwsProperties {
    private String accessKey;
    private String secretKey;
    private String region;
    private S3 s3 = new S3(); // Nested object

    // Getters and Setters are MANDATORY for Spring to bind values!
    public String getAccessKey() { return accessKey; }
    public void setAccessKey(String accessKey) { this.accessKey = accessKey; }
    public String getSecretKey() { return secretKey; }
    public void setSecretKey(String secretKey) { this.secretKey = secretKey; }
    public String getRegion() { return region; }
    public void setRegion(String region) { this.region = region; }
    public S3 getS3() { return s3; }
    public void setS3(S3 s3) { this.s3 = s3; }

    public static class S3 {
        private String bucket;
        private int timeout;
        // Getters and setters for these...
    }
}

Step 3: Using it in your Service

java

@Service
public class AwsUploader {
    private final AwsProperties awsProperties;

    public AwsUploader(AwsProperties awsProperties) {
        this.awsProperties = awsProperties;
    }

    public void upload() {
        // Clean, type-safe access!
        String key = awsProperties.getAccessKey();
        String bucket = awsProperties.getS3().getBucket();
        System.out.println("Uploading to bucket: " + bucket);
    }
}

Why is this amazing? If you misspell acess-key in your YAML, Spring throws a clear startup error, rather than failing silently at runtime.

Part 3: Java Configuration (@Configuration classes)

This is NOT for data values (ports, URLs). This is for defining Beans (objects) that your app needs.

Remember the @Component lesson? You can't put @Component on third-party classes like RestTemplate. So you use @Configuration to explicitly create them.

java

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestTemplate;

@Configuration // Tells Spring: "This class contains Bean definitions"
public class AppConfig {

    // Creates a Bean and registers it in the Spring Container
    @Bean
    public RestTemplate restTemplate() {
        System.out.println("RestTemplate Bean created via @Configuration!");
        return new RestTemplate();
    }

    // You can even use configuration VALUES inside @Bean creation!
    @Bean
    public DataSource dataSource() {
        // Imagine we injected the AwsProperties here...
        return DataSourceBuilder.create()
                .url("jdbc:mysql://localhost:3306/mydb") // Usually read from @Value
                .build();
    }
}

Part 4: Profiles (Dev vs Prod)

You don't want to manually comment/uncomment URLs when deploying. Spring Boot has Profiles.

File 1: application-dev.yml (Runs on my laptop)

yaml

server:
  port: 8080
spring:
  datasource:
    url: jdbc:h2:mem:testdb

File 2: application-prod.yml (Runs in the cloud)

yaml

server:
  port: 443
spring:
  datasource:
    url: jdbc:mysql://production-db.amazonaws.com:3306/mydb

How to activate them:

  • In IntelliJ VM options: Dspring.profiles.active=dev
  • In your application.yml base file: spring.profiles.active: prod
  • Command line: java -jar myapp.jar --spring.profiles.active=prod

Part 5: The Magic Override Hierarchy (Crucial for DevOps)

Here is the secret superpower of Spring Boot: You can override any application.yml value without rebuilding the JAR.

Spring Boot reads configuration in this exact order (higher overrides lower):

  1. Command Line Arguments (Highest priority): java -jar app.jar --server.port=9090
  1. Environment Variables (used in Kubernetes/Docker): export SERVER_PORT=9090
  1. application-{profile}.yml (e.g., application-prod.yml)
  1. application.yml (Lowest priority - the default)

Practical DevOps example: You NEVER hardcode production passwords in application.yml. You set them as Environment Variables in your cloud server:

bash

export SPRING_DATASOURCE_PASSWORD=SuperSecret2024! # Boot automatically maps this to spring.datasource.password
java -jar myapp.jar

The "Gotcha" You Must Remember

@Configuration vs @Component - We touched on this in Beans, but it's critical here:

  • If you put @Bean methods inside a @Configuration class, Spring wraps the class with a CGLIB proxy. Calling restTemplate() inside another @Bean method returns the same Singleton instance.
  • If you put @Bean methods inside a @Component class, Spring does NOT proxy it. Calling the method returns a new instance every time, breaking Singleton behavior.

java

@Configuration // CORRECT - Singleton guaranteed
public class CorrectConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); } // Gets cached A
}

@Component // WRONG for cross-bean references
public class WrongConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); } // Creates a SECOND A instance! Bug!
}

5. Dependency injection

Open Original Article

Dependency injection

Dependency Injection (DI) is a design pattern implementing Inversion of Control (IoC), where the Spring container automatically creates and manages object dependencies, injecting them at runtime rather than having classes instantiate them directly.

  • The Concept: Instead of a class using the new keyword to create its collaborators, Spring's IoC container wires them together based on configurations or annotations.
  • The Benefit: It promotes loose coupling, making code highly modular, maintainable, and easy to unit test by swapping real dependencies with mocks.

The "Warehouse" (IoC Container)

When your Spring Boot app starts, it scans all your classes. Any class annotated with @Component, @Service, @Repository, or @Controller is instantiated and placed into Spring's IoC Container (think of it as a giant global HashMap of ready-to-use objects).

Primary Injection Types:

Constructor Injection
Dependencies are passed through the class constructor. Spring automatically resolves the parameters when instantiating the bean. Since Spring 4.3, the @Autowired annotation is optional if the class has only a single constructor. This approach is strongly recommended because it guarantees that dependencies are not null and allows fields to be marked as final, ensuring immutability and making unit testing straightforward without needing a Spring container.

Java

@Service
public class UserService{
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository){
        this.userRepository = userRepository;
    }

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Setter Injection
Dependencies are assigned via public setter methods after the bean is created using a default no-arg constructor. This method is ideal for optional dependencies or circular dependencies where components need to be modified or injected after initial bean construction. It requires placing the @Autowired annotation explicitly on the setter method.

Java

@Service
public class UserService{
    private UserRepository userRepository;

    @Autowired
    public void setUserRepository(UserRepository userRepository){
        this.userRepository = userRepository;
    }

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Field Injection
Dependencies are injected directly into class variables using reflection, completely bypassing constructors and setters. While it reduces boilerplate code, it is widely discouraged in production codebases. Field injection hides tight coupling, makes classes difficult to instantiate manually in unit tests (requiring reflection or mocking frameworks to set private fields), and prevents fields from being declared final. It requires the @Autowired annotation directly above the field.

Java

@Service
public class UserService{
    @Autowired
    private UserRepository userRepository;

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Prioritizing constructor injection for all mandatory components ensures a clean, predictable component lifecycle and robust, testable code.

The "Magic" (How Spring finds them)

Notice in the Constructor example I did not write @Autowired on the constructor. Why?

Because if a class has only one constructor, Spring Boot automatically uses it to inject dependencies. If you have multiple constructors, you must put @Autowired on the one you want Spring to use.

The Golden Rule for DI in Spring Boot:

Never use new to create a Service, Repository, or Controller. Always let Spring inject them via the constructor. If you need to create an object manually (like a simple DTO or a LocalDate), that's fine—those aren't "dependencies" and don't go in the container.

Profiles

Part 1: The Core Mechanism (Naming Convention)

Spring Boot uses a simple file-naming rule. Instead of having just one application.yml, you create multiple:

File NamePurpose
application.ymlThe default/base file (shared by all profiles).
application-dev.ymlOverrides specifically for Development (local laptop).
application-test.ymlOverrides specifically for Testing (QA server).
application-prod.ymlOverrides specifically for Production (Live users).

Both application.yml (YAML) and application.properties serve the same fundamental purpose in Spring Boot: defining externalized configuration settings. However, they differ in syntax, readability, features, and how Spring Boot parses them.

1. Syntax Comparison

YAML uses indentation (spaces, not tabs) to represent hierarchical data, while .properties uses flat key=value pairs.

Properties (application.properties)

Properties

server.port=8080
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=secret

# List values
app.allowed-origins[0]=https://example.com
app.allowed-origins[1]=https://api.example.com

YAML (application.yml)

YAML

server:
  port: 8080

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret

# List values
app:
  allowed-origins:
    - https://example.com
    - https://api.example.com


Example Of different profiles : The Base File (application.yml)

yaml

# These apply to EVERY profile, unless overridden
server:
  port: 8080

app:
  name: MyEcommerceApp
  cache:
    enabled: true

yaml

# Runs on my laptop - uses an in-memory database

  port: 9090  # Overrides the base port 8080

  datasource:
    url: jdbc:h2:mem:devdb
    username: sa
    password:
  jpa:

yaml

Part 2: How to Activate a Profile (The 3 Ways)

Spring Boot needs to know which file to load. You tell it by setting spring.profiles.active.

Method 1: Command Line (Best for DevOps/Docker)

bash

java -jar myapp.jar --spring.profiles.active=prod

Method 2: Environment Variable (Best for Kubernetes/Cloud)

bash

export SPRING_PROFILES_ACTIVE=prod
java -jar myapp.jar

Method 3: Hardcode in application.yml (Only for local testing)

yaml

spring:
  profiles:
    active: dev  # My laptop always uses dev

Part 3: Profile-Specific Beans (@Profile annotation)

Sometimes, you don't just change a URL—you need to inject completely different Java objects depending on the environment.

Example: In Dev, you want to use a fake "Stub" email sender (so you don't accidentally spam real customers). In Prod, you use the real AWS SES sender.

java

// 1. The Interface
public interface EmailSender {
    void send(String message);
}

// 2. The DEV Implementation (Fake)
@Component
@Profile("dev") // Spring ONLY creates this bean if "dev" is active!
public class DevEmailSender implements EmailSender {
    @Override
    public void send(String message) {
        System.out.println("[DEV STUB] Would send email: " + message);
        // No actual network calls. Safe for testing.
    }
}

// 3. The PROD Implementation (Real)
@Component
@Profile("prod") // Spring ONLY creates this bean if "prod" is active!
public class ProdEmailSender implements EmailSender {
    @Override
    public void send(String message) {
        // Actual AWS SDK code to send a real email.
        System.out.println("SENDING REAL EMAIL TO CUSTOMER: " + message);
    }
}

// 4. The Service (Doesn't care which one it gets)
@Service
public class NotificationService {
    private final EmailSender emailSender;

    public NotificationService(EmailSender emailSender) {
        this.emailSender = emailSender; // Gets Dev bean in dev, Prod bean in prod.
    }
}

Part 4: Spring Boot 2.4+ "Profile Groups" (The Pro Feature)

In large projects, "prod" might mean 10 different microservices. Instead of writing @Profile("prod") on 50 beans, you group them.

yaml

# Inside application.yml
spring:
  profiles:
    groups:
      # If I activate "cloud", it automatically activates "prod" AND "aws" AND "monitoring"
      cloud: prod, aws, monitoring
      local: dev, h2, debug

# Now when you run: java -jar app.jar --spring.profiles.active=cloud
# Spring Boot automatically loads: application-prod.yml, application-aws.yml, AND application-monitoring.yml

Why this is awesome: You can mix-and-match features. You can reuse aws.yml for both Prod and Staging without duplicating code.

Part 5: The "Default" Profile

What if you don't set spring.profiles.active? Spring Boot uses a default profile called default.

  • You can define fallback properties inside application.yml specifically for this:

yaml

# This only runs if NO profile is active (i.e., default)
spring:
  config:
    activate:
      on-profile: default
server:
  port: 8080

(Practical tip: In real projects, you always set a profile. The "default" profile is usually just a safety net to prevent startup failures.)

Part 6: Testing with Profiles

In your integration tests, you don't want to accidentally connect to the real production database. You specify a test profile.

java

@SpringBootTest
@ActiveProfiles("test") // Tells Spring: "Load application-test.yml for this test"
public class UserServiceTest {

    @Test
    void testSomething() {
        // This uses the H2 database, not MySQL.
    }
}



Configuration Precedence Order :

When properties with the same key exist across default and profile-specific files, lower precedence properties are overwritten by higher precedence ones:

  • Lowest: Base application.properties / application.yml (Default settings loaded for all profiles).
  • Higher: Profile-specific files (application-{profile}.properties / .yml).
  • Highest: Command-line arguments, environment variables, or System properties set at launch.

If multiple profiles are active (e.g., --spring.profiles.active=dev,h2), the profile listed last wins in case of key collisions.

2. Multi-Profile Layering Example

Properties are layered dynamically at runtime rather than inherited:

application.yml (Default base config)

YAML

app:
  name: "My App"
  max-connections: 10
  feature-flag: false

application-dev.yml (Activated via dev profile)

YAML

app:
  max-connections: 50
  feature-flag: true
  • Active profile: dev
  • Resolved app.name: "My App" (inherited from default because dev doesn't redefine it)
  • Resolved app.max-connections: 50 (profile property overrides base property)
  • Resolved app.feature-flag: true (profile property overrides base property)

Breaking Down Each Component (Practical Usage)

1. The "Root" Package (com.example.myapp)

  • Practical rule: Everything must be inside or below this package.
  • Why? Spring Boot's @ComponentScan starts scanning from this package by default. If you put a Service outside this folder, Spring won't find it, and you'll get cryptic NoSuchBeanDefinitionException errors.

2. The Main Class (MySpringBootApplication.java)

java

@SpringBootApplication  // This is a triple-annotation: @Configuration + @EnableAutoConfiguration + @ComponentScan
public class MySpringBootApplication {
    public static void main(String[] args) {
        SpringApplication.run(MySpringBootApplication.class, args);
    }
}
  • Practical placement: This file must be at the root of your package structure (directly under com.example.myapp).
  • Why? Because @SpringBootApplication scans all sub-packages (controller, service, repository) recursively. If you move this into a sub-folder, none of your beans get loaded.

3. The "Layered" Sub-Packages (Controller, Service, Repository)

This is the classic 3-tier architecture:

FolderPurposeKey Annotation
controller/Handles HTTP requests/responses (REST endpoints).@RestController, @RequestMapping
service/Houses business logic (calculations, validations, orchestration).@Service
repository/Talks to the database (CRUD operations).@Repository or public interface JpaRepository
model/Plain POJOs (Entities, DTOs).@Entity (JPA) or just plain Java classes.
config/Custom beans that override Boot's defaults (e.g., custom SecurityFilterChain, RestTemplate).@Configuration

Practical rule: Never put business logic in the Controller. Keep Controller thin (just parse input, call Service, return JSON). This makes unit testing easy.

4. The resources/ Folder (The Brain)

This is where your external configuration lives. It is not Java code; it is runtime data.

  • application.yml (or .properties): This is the single source of truth for environment-specific settings.
    • Example: server.port: 8081, spring.datasource.url: jdbc:mysql://localhost:3306/mydb.
    • Practical trick: You can have application-dev.yml, application-prod.yml and activate them using spring.profiles.active=dev.
  • static/: Put your frontend static assets here (CSS, JavaScript, images). They are served automatically at http://localhost:8080/css/style.css.
  • templates/: Put your server-side rendering HTML here (Thymeleaf or JSP). Boot auto-configures the ViewResolver to look here.
  • db/migration/: If you use Flyway, put your SQL migration scripts here (e.g., V1__create_users_table.sql). Boot runs them automatically on startup.

5. The test/ Folder (Parallel Structure)

  • It mirrors the main/java structure exactly.
  • Crucial file: MySpringBootApplicationTests.java – this is the "sanity check" test. It loads the entire Spring context to ensure your database connections and beans all wire up correctly.
  • Practical use: Always run this test before pushing to Git. If this test fails, your application won't even start in production.

Spring vs Spring Boot

The 30-Second Elevator Pitch

"Spring is a comprehensive Java framework designed to build enterprise applications through features like Dependency Injection (DI) and Inversion of Control (IoC). However, standard Spring requires extensive manual configuration.
Spring Boot is an extension built on top of the Spring Framework that eliminates boilerplate configuration. It provides auto-configuration, starter dependencies, and embedded servers to let developers create production-ready microservices and web applications out of the box."
