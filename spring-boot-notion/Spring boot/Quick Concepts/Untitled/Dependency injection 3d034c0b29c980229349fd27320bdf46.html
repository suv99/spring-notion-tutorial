Dependency injection

Dependency Injection (DI) is a design pattern implementing Inversion of Control (IoC), where the Spring container automatically creates and manages object dependencies, injecting them at runtime rather than having classes instantiate them directly.

  • The Concept: Instead of a class using the new keyword to create its collaborators, Spring's IoC container wires them together based on configurations or annotations.
  • The Benefit: It promotes loose coupling, making code highly modular, maintainable, and easy to unit test by swapping real dependencies with mocks.

The "Warehouse" (IoC Container)

When your Spring Boot app starts, it scans all your classes. Any class annotated with @Component, @Service, @Repository, or @Controller is instantiated and placed into Spring's IoC Container (think of it as a giant global HashMap of ready-to-use objects).

Primary Injection Types:

Constructor Injection
Dependencies are passed through the class constructor. Spring automatically resolves the parameters when instantiating the bean. Since Spring 4.3, the @Autowired annotation is optional if the class has only a single constructor. This approach is strongly recommended because it guarantees that dependencies are not null and allows fields to be marked as final, ensuring immutability and making unit testing straightforward without needing a Spring container.

Java

@Service
public class UserService{
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository){
        this.userRepository = userRepository;
    }

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Setter Injection
Dependencies are assigned via public setter methods after the bean is created using a default no-arg constructor. This method is ideal for optional dependencies or circular dependencies where components need to be modified or injected after initial bean construction. It requires placing the @Autowired annotation explicitly on the setter method.

Java

@Service
public class UserService{
    private UserRepository userRepository;

    @Autowired
    public void setUserRepository(UserRepository userRepository){
        this.userRepository = userRepository;
    }

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Field Injection
Dependencies are injected directly into class variables using reflection, completely bypassing constructors and setters. While it reduces boilerplate code, it is widely discouraged in production codebases. Field injection hides tight coupling, makes classes difficult to instantiate manually in unit tests (requiring reflection or mocking frameworks to set private fields), and prevents fields from being declared final. It requires the @Autowired annotation directly above the field.

Java

@Service
public class UserService{
    @Autowired
    private UserRepository userRepository;

    public User getUser(Long id){
        return userRepository.findById(id);
    }
}

Prioritizing constructor injection for all mandatory components ensures a clean, predictable component lifecycle and robust, testable code.

The "Magic" (How Spring finds them)

Notice in the Constructor example I did not write @Autowired on the constructor. Why?

Because if a class has only one constructor, Spring Boot automatically uses it to inject dependencies. If you have multiple constructors, you must put @Autowired on the one you want Spring to use.

The Golden Rule for DI in Spring Boot:

Never use new to create a Service, Repository, or Controller. Always let Spring inject them via the constructor. If you need to create an object manually (like a simple DTO or a LocalDate), that's fine—those aren't "dependencies" and don't go in the container.
