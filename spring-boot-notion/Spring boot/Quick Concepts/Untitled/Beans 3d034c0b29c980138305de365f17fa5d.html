Beans

In plain English: A Spring Bean is simply a Java object that Spring manages for you.

Normally, you do MyClass obj = new MyClass(). With Spring Boot, you let Spring create and hold the object in its IoC Container (the "warehouse"). Whenever you need it, Spring hands it to you (Dependency Injection).

Here is the golden rule: Every Service, Repository, Controller, Configuration, and Component you write is a Bean.

But how do you tell Spring to manage an object? There are two distinct ways, and you must know both.

Method 1: Class-Level Annotations (The Easy 95% Way)

You put an annotation directly on your class. Spring scans the package, finds it, and creates a Bean automatically.

AnnotationWhat it means practicallyWhen to use
@Component"Spring, manage this generic class."Utility classes, helpers.
@Service"Spring, manage this as business logic."All your business logic classes.
@Repository"Spring, manage this for DB access."JPA Repositories, DAO classes. (Also catches DB exceptions).
@Controller / @RestController"Spring, manage this as a web endpoint."REST API controllers.
// 1. Tell Spring to manage this class as a Bean
@Service 
public class TaxCalculator {

    // No @Autowired needed on constructor for a single constructor
    public TaxCalculator() {
        System.out.println("TaxCalculator Bean Created!");
    }

    public double calculate(double amount) {
        return amount * 0.18;
    }
}

// 2. Some other class asks for it
@RestController
public class BillController {
    private final TaxCalculator taxCalculator;

    // Spring injects the TaxCalculator Bean here
    public BillController(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }
}

Method 2: The @Bean Method (The Explicit 5% Way)

You cannot put @Component on third-party classes (like RestTemplate, ObjectMapper, or AmazonS3Client) because you don't own the source code!

The Limitation: First-Party vs. Third-Party Code

  • First-Party Code (Your Code): You wrote it. You can open UserService.java in your IDE and put @Component or @Service directly above the class definition. Spring scans your project, finds the annotation, and creates the bean.
  • Third-Party Code (External Libraries): These are pre-compiled and read-only. You cannot open the class file for RestTemplate or ObjectMapper to add annotations to it.

For these, you manually tell Spring: "Hey, when I call this method, take the object it returns and manage it as a Bean."

You do this inside a class annotated with @Configuration.

The Solution: @Configuration and @Bean

Because you cannot tell the third-party class to register itself, you must tell Spring how to create an instance of it inside your own code using a @Configuration class and a @Bean method:

Java

@Configuration
public class AppConfig{

    // Spring runs this method and manages the returned instance as a bean
    @Bean
    public RestTemplate restTemplate(){
        return new RestTemplate();
    }

    @Bean
    public ObjectMapper objectMapper(){
        return new ObjectMapper();
    }
}

Once defined this way, Spring places these instances into the ApplicationContext, allowing you to inject them into your services just like any other @Component:

Java

@Service
@RequiredArgsConstructor
public class ApiClientService{

    private final RestTemplate restTemplate; // Injected automatically
    private final ObjectMapper objectMapper; // Injected automatically
}

The Most Important Spring Boot Twist: @ConditionalOnMissingBean

This is what makes Spring Boot magical. When you autowire a Bean, Spring Boot says: "I have a default Bean, but if you create your own, I'll use yours instead."

Spring Boot has auto-configuration classes running in the background for common infrastructure (like Jackson's ObjectMapper, a DataSource, or builders).

Almost every default bean definition in Spring Boot is marked with this annotation:

Java

@Bean
@ConditionalOnMissingBean // "Only create this if the user hasn't created one!"
public ObjectMapper objectMapper(){
    return new ObjectMapper();
}

When your application boots up:

  1. Spring checks your code first: Did you declare your own @Bean for that class?
  1. If YES: Spring registers your bean. The conditional check fails, so Spring Boot backs off and does not create its default.
  1. If NO: Spring Boot creates and registers its default bean for you.

an example where Spring Boot does provide a full default bean that completely steps aside when you write yours, look at Jackson's ObjectMapper:

Java

@Configuration
public class JacksonConfig{

    // The moment you define this, Spring Boot disables its auto-configured ObjectMapper
    @Bean
    public ObjectMapper customObjectMapper(){
        ObjectMapper mapper = new ObjectMapper();
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        return mapper;
    }
}

Without this method, Spring Boot supplies a default ObjectMapper. With this method present, Spring Boot's @ConditionalOnMissingBean detects your bean, backs off, and wires your custom version everywhere across your application.

Bean Scopes (Singleton vs Prototype)

By default, every Bean in Spring Boot is a Singleton. This means Spring creates only one instance of that class for the entire application, and every class that injects it gets the exact same object in memory.

Singleton Scope (Default)
When a bean is defined as a singleton, the Spring container creates only one shared instance of that bean for the entire application context. Every time that bean is requested or injected anywhere in your code, Spring returns the exact same object reference. This is ideal for stateless components like service layers, data access objects (DAOs), and utility beans.

Prototype Scope
When a bean is configured as a prototype, a brand-new instance is created every single time the bean is requested from the container. If you inject or request a prototype bean in multiple places, you receive a completely distinct object instance each time. This is necessary for stateful objects where data shouldn't be shared or overwritten globally.

Code Example

Java

@Component
// Singleton scope (default) - only one instance exists application-wide
public class InventoryService{
    public void checkStock(){
        // Stateless business logic
    }
}

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
// Prototype scope - a fresh instance is generated on every request
public class ShoppingCart{
    private List<String> items = new ArrayList<>();

    public void addItem(String item){
        items.add(item);
    }
}

In this setup, InventoryService is shared safely across the application since it doesn't hold user-specific data. Conversely, ShoppingCart maintains user-specific state, meaning a prototype scope ensures different threads or user sessions receive independent carts rather than conflicting over the same instance.

Bean Naming (The Silent Bug Maker)

If you don't specify a name, Spring Boot uses camelCase of the class name.

  • TaxCalculator class → Bean name is taxCalculator
  • RestTemplate class → Bean name is restTemplate

How does Spring inject dependencies? Does it check the type or the name?

Resolution Order

When Spring encounters an injection point (like @Autowired), it resolves candidates through a fixed sequence:

  1. Match by Type: Spring scans the ApplicationContext for all beans assignable to the target dependency's type (including interfaces and parent classes).
    • Exactly 1 match: It injects that bean directly.
    • 0 matches: It throws NoSuchBeanDefinitionException.
    • 2 or more matches: It moves to ambiguity resolution.
  1. Check for @Primary: If multiple beans match the type, Spring checks whether exactly one of them is annotated with @Primary. If so, that bean wins.
  1. Check for @Qualifier: If specified at the injection point (e.g., @Qualifier("creditCardService")), Spring matches against the qualifier value declared on the candidate bean.
  1. Fallback: Match by Name: If multiple candidate beans match the type and no @Primary or @Qualifier settles it, Spring compares the field or parameter name to the candidate bean names (IDs).
    • If one candidate's bean ID matches the variable name, it injects it.
    • If none or multiple match, it throws NoUniqueBeanDefinitionException.
public interface PaymentGateway {}

@Component("stripe")
public class StripeGateway implements PaymentGateway {}

@Component("paypal")
public class PayPalGateway implements PaymentGateway {}

@Service
public class CheckoutService {

    // 1. Spring looks for beans of type PaymentGateway -> finds [stripe, paypal]
    // 2. Ambiguity exists -> checks variable name: "paypal"
    // 3. Injects PayPalGateway
    @Autowired
    private PaymentGateway paypal; 
}
