Profiles

Part 1: The Core Mechanism (Naming Convention)

Spring Boot uses a simple file-naming rule. Instead of having just one application.yml, you create multiple:

File NamePurpose
application.ymlThe default/base file (shared by all profiles).
application-dev.ymlOverrides specifically for Development (local laptop).
application-test.ymlOverrides specifically for Testing (QA server).
application-prod.ymlOverrides specifically for Production (Live users).

Both application.yml (YAML) and application.properties serve the same fundamental purpose in Spring Boot: defining externalized configuration settings. However, they differ in syntax, readability, features, and how Spring Boot parses them.

1. Syntax Comparison

YAML uses indentation (spaces, not tabs) to represent hierarchical data, while .properties uses flat key=value pairs.

Properties (application.properties)

Properties

server.port=8080
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=secret

# List values
app.allowed-origins[0]=https://example.com
app.allowed-origins[1]=https://api.example.com

YAML (application.yml)

YAML

server:
  port: 8080

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret

# List values
app:
  allowed-origins:
    - https://example.com
    - https://api.example.com


Example Of different profiles : The Base File (application.yml)

yaml

# These apply to EVERY profile, unless overridden
server:
  port: 8080

app:
  name: MyEcommerceApp
  cache:
    enabled: true

Example: The Dev File (application-dev.yml)

yaml

# Runs on my laptop - uses an in-memory database
server:
  port: 9090  # Overrides the base port 8080

spring:
  datasource:
    url: jdbc:h2:mem:devdb
    username: sa
    password:
  jpa:
    show-sql: true  # I want to see every SQL query for debugging

logging:
  level:
    com.myapp: DEBUG  # Super verbose logs

Example: The Prod File (application-prod.yml)

yaml

# Runs on the cloud server
spring:
  datasource:
    url: jdbc:mysql://prod-db.amazonaws.com:3306/mydb
    username: ${DB_USER}  # Reads from secret environment variables
    password: ${DB_PASS}
  jpa:
    show-sql: false  # Hide SQL in production to reduce log noise

logging:
  level:
    com.myapp: WARN  # Only log warnings and errors

server:
  compression:
    enabled: true  # Enable GZIP compression for faster load times

Part 2: How to Activate a Profile (The 3 Ways)

Spring Boot needs to know which file to load. You tell it by setting spring.profiles.active.

Method 1: Command Line (Best for DevOps/Docker)

bash

java -jar myapp.jar --spring.profiles.active=prod

Method 2: Environment Variable (Best for Kubernetes/Cloud)

bash

export SPRING_PROFILES_ACTIVE=prod
java -jar myapp.jar

Method 3: Hardcode in application.yml (Only for local testing)

yaml

spring:
  profiles:
    active: dev  # My laptop always uses dev

Part 3: Profile-Specific Beans (@Profile annotation)

Sometimes, you don't just change a URL—you need to inject completely different Java objects depending on the environment.

Example: In Dev, you want to use a fake "Stub" email sender (so you don't accidentally spam real customers). In Prod, you use the real AWS SES sender.

java

// 1. The Interface
public interface EmailSender {
    void send(String message);
}

// 2. The DEV Implementation (Fake)
@Component
@Profile("dev") // Spring ONLY creates this bean if "dev" is active!
public class DevEmailSender implements EmailSender {
    @Override
    public void send(String message) {
        System.out.println("[DEV STUB] Would send email: " + message);
        // No actual network calls. Safe for testing.
    }
}

// 3. The PROD Implementation (Real)
@Component
@Profile("prod") // Spring ONLY creates this bean if "prod" is active!
public class ProdEmailSender implements EmailSender {
    @Override
    public void send(String message) {
        // Actual AWS SDK code to send a real email.
        System.out.println("SENDING REAL EMAIL TO CUSTOMER: " + message);
    }
}

// 4. The Service (Doesn't care which one it gets)
@Service
public class NotificationService {
    private final EmailSender emailSender;

    public NotificationService(EmailSender emailSender) {
        this.emailSender = emailSender; // Gets Dev bean in dev, Prod bean in prod.
    }
}

Part 4: Spring Boot 2.4+ "Profile Groups" (The Pro Feature)

In large projects, "prod" might mean 10 different microservices. Instead of writing @Profile("prod") on 50 beans, you group them.

yaml

# Inside application.yml
spring:
  profiles:
    groups:
      # If I activate "cloud", it automatically activates "prod" AND "aws" AND "monitoring"
      cloud: prod, aws, monitoring
      local: dev, h2, debug

# Now when you run: java -jar app.jar --spring.profiles.active=cloud
# Spring Boot automatically loads: application-prod.yml, application-aws.yml, AND application-monitoring.yml

Why this is awesome: You can mix-and-match features. You can reuse aws.yml for both Prod and Staging without duplicating code.

Part 5: The "Default" Profile

What if you don't set spring.profiles.active? Spring Boot uses a default profile called default.

  • You can define fallback properties inside application.yml specifically for this:

yaml

# This only runs if NO profile is active (i.e., default)
spring:
  config:
    activate:
      on-profile: default
server:
  port: 8080

(Practical tip: In real projects, you always set a profile. The "default" profile is usually just a safety net to prevent startup failures.)

Part 6: Testing with Profiles

In your integration tests, you don't want to accidentally connect to the real production database. You specify a test profile.

java

@SpringBootTest
@ActiveProfiles("test") // Tells Spring: "Load application-test.yml for this test"
public class UserServiceTest {

    @Test
    void testSomething() {
        // This uses the H2 database, not MySQL.
    }
}



Configuration Precedence Order :

When properties with the same key exist across default and profile-specific files, lower precedence properties are overwritten by higher precedence ones:

  • Lowest: Base application.properties / application.yml (Default settings loaded for all profiles).
  • Higher: Profile-specific files (application-{profile}.properties / .yml).
  • Highest: Command-line arguments, environment variables, or System properties set at launch.

If multiple profiles are active (e.g., --spring.profiles.active=dev,h2), the profile listed last wins in case of key collisions.

2. Multi-Profile Layering Example

Properties are layered dynamically at runtime rather than inherited:

application.yml (Default base config)

YAML

app:
  name: "My App"
  max-connections: 10
  feature-flag: false

application-dev.yml (Activated via dev profile)

YAML

app:
  max-connections: 50
  feature-flag: true
  • Active profile: dev
  • Resolved app.name: "My App" (inherited from default because dev doesn't redefine it)
  • Resolved app.max-connections: 50 (profile property overrides base property)
  • Resolved app.feature-flag: true (profile property overrides base property)
