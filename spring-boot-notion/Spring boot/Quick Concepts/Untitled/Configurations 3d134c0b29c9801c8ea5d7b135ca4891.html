Configurations

To understand Spring Boot Configuration, think of it as the "control panel" of your application.

It is everything that determines HOW your app runs, without changing your Java source code. Do you need to run on port 8081 instead of 8080? Change the database URL? Turn on debug logs? That is all Configuration.

In Spring Boot, configuration is split into two completely different worlds. Mixing them up is the #1 mistake junior developers make:

  1. Externalized Configuration (Data/Values): Database URLs, API keys, server ports. Lives in application.properties / application.yml.
  1. Java Configuration (Beans/Setup): Creating and wiring up Beans (like RestTemplate, SecurityFilterChain). Lives in classes annotated with @Configuration.

Here is exactly how both work, with rock-solid examples.

Part 1: Externalized Configuration (The application.yml file)

This is where you store values that change per environment (Dev, QA, Prod). Spring Boot reads this file automatically on startup.

Example using application.yml (modern) vs application.properties (older):

Old way (properties - flat & repetitive):

properties

server.port=8081
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=secret123

New way (YAML - hierarchical & human-readable):

yaml

server:
  port: 8081

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret123

# Custom application-specific settings
app:
  name: E-Commerce API
  max-retry-attempts: 3
  email:
    host: smtp.gmail.com
    port: 587

Part 2: Reading Configuration in Your Java Code

You never hardcode "localhost" or "8081" in your classes. You read them from the YAML file using two methods:

Method A: @Value (Use for 1–2 simple values)

java

@Service
public class EmailService {

    @Value("${app.email.host}")   // Reads "smtp.gmail.com"
    private String emailHost;

    @Value("${app.email.port}")   // Reads "587"
    private int emailPort;

    @Value("${app.max-retry-attempts:5}") // Reads 3, but defaults to 5 if missing!
    private int maxRetries;

    public void send() {
        System.out.println("Connecting to " + emailHost + ":" + emailPort);
    }
}

Downside: If you have 20 related properties, your class gets cluttered with 20 @Value annotations.

Method B: @ConfigurationProperties (The PRO Way - USE THIS!)

This binds a whole group of properties into a single, type-safe Java POJO. This is the gold standard in professional Spring Boot.

Step 1: The properties file (application.yml)

yaml

aws:
  access-key: AKIAIOSFODNN7EXAMPLE
  secret-key: wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
  region: us-east-1
  s3:
    bucket: my-app-bucket
    timeout: 3000

Step 2: The Java POJO to hold them

java

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.stereotype.Component;

@Component
@ConfigurationProperties(prefix = "aws") // Tells Spring to map everything under "aws"
public class AwsProperties {
    private String accessKey;
    private String secretKey;
    private String region;
    private S3 s3 = new S3(); // Nested object

    // Getters and Setters are MANDATORY for Spring to bind values!
    public String getAccessKey() { return accessKey; }
    public void setAccessKey(String accessKey) { this.accessKey = accessKey; }
    public String getSecretKey() { return secretKey; }
    public void setSecretKey(String secretKey) { this.secretKey = secretKey; }
    public String getRegion() { return region; }
    public void setRegion(String region) { this.region = region; }
    public S3 getS3() { return s3; }
    public void setS3(S3 s3) { this.s3 = s3; }

    public static class S3 {
        private String bucket;
        private int timeout;
        // Getters and setters for these...
    }
}

Step 3: Using it in your Service

java

@Service
public class AwsUploader {
    private final AwsProperties awsProperties;

    public AwsUploader(AwsProperties awsProperties) {
        this.awsProperties = awsProperties;
    }

    public void upload() {
        // Clean, type-safe access!
        String key = awsProperties.getAccessKey();
        String bucket = awsProperties.getS3().getBucket();
        System.out.println("Uploading to bucket: " + bucket);
    }
}

Why is this amazing? If you misspell acess-key in your YAML, Spring throws a clear startup error, rather than failing silently at runtime.

Part 3: Java Configuration (@Configuration classes)

This is NOT for data values (ports, URLs). This is for defining Beans (objects) that your app needs.

Remember the @Component lesson? You can't put @Component on third-party classes like RestTemplate. So you use @Configuration to explicitly create them.

java

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestTemplate;

@Configuration // Tells Spring: "This class contains Bean definitions"
public class AppConfig {

    // Creates a Bean and registers it in the Spring Container
    @Bean
    public RestTemplate restTemplate() {
        System.out.println("RestTemplate Bean created via @Configuration!");
        return new RestTemplate();
    }

    // You can even use configuration VALUES inside @Bean creation!
    @Bean
    public DataSource dataSource() {
        // Imagine we injected the AwsProperties here...
        return DataSourceBuilder.create()
                .url("jdbc:mysql://localhost:3306/mydb") // Usually read from @Value
                .build();
    }
}

Part 4: Profiles (Dev vs Prod)

You don't want to manually comment/uncomment URLs when deploying. Spring Boot has Profiles.

File 1: application-dev.yml (Runs on my laptop)

yaml

server:
  port: 8080
spring:
  datasource:
    url: jdbc:h2:mem:testdb

File 2: application-prod.yml (Runs in the cloud)

yaml

server:
  port: 443
spring:
  datasource:
    url: jdbc:mysql://production-db.amazonaws.com:3306/mydb

How to activate them:

  • In IntelliJ VM options: Dspring.profiles.active=dev
  • In your application.yml base file: spring.profiles.active: prod
  • Command line: java -jar myapp.jar --spring.profiles.active=prod

Part 5: The Magic Override Hierarchy (Crucial for DevOps)

Here is the secret superpower of Spring Boot: You can override any application.yml value without rebuilding the JAR.

Spring Boot reads configuration in this exact order (higher overrides lower):

  1. Command Line Arguments (Highest priority): java -jar app.jar --server.port=9090
  1. Environment Variables (used in Kubernetes/Docker): export SERVER_PORT=9090
  1. application-{profile}.yml (e.g., application-prod.yml)
  1. application.yml (Lowest priority - the default)

Practical DevOps example: You NEVER hardcode production passwords in application.yml. You set them as Environment Variables in your cloud server:

bash

export SPRING_DATASOURCE_PASSWORD=SuperSecret2024! # Boot automatically maps this to spring.datasource.password
java -jar myapp.jar

The "Gotcha" You Must Remember

@Configuration vs @Component - We touched on this in Beans, but it's critical here:

  • If you put @Bean methods inside a @Configuration class, Spring wraps the class with a CGLIB proxy. Calling restTemplate() inside another @Bean method returns the same Singleton instance.
  • If you put @Bean methods inside a @Component class, Spring does NOT proxy it. Calling the method returns a new instance every time, breaking Singleton behavior.

java

@Configuration // CORRECT - Singleton guaranteed
public class CorrectConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); } // Gets cached A
}

@Component // WRONG for cross-bean references
public class WrongConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); } // Creates a SECOND A instance! Bug!
}
